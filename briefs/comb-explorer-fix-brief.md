# Brief: comb explorer, revision 1 — flat rendering (no DOM nesting per level), path-only expansion on go-to, and an explicit reading of comma input — for the delegated session that built `viz/comb_explorer.html`

**Context:** `briefs/comb-explorer-brief.md` and `briefs/comb-explorer-findings.md` (what was built), `viz/comb_explorer.html` as merged on `main` at `f5c31d3`, `experiments/comb_explorer_check.py`, `comb.md` §18. House rules as in the original brief.

## The defect (the author's report, 2026-09-15)

The author typed `137,517` into the go-to box and the page crashed. The arithmetic is not at fault: under node, `pathToRoot(137n, 517n)` returns a path of `1,365` nodes (`λ = 1364`, `η = 1056`, largest peak `249` digits) in `4 ms`, the children of every ancestor in `14 ms`, the raw descent (`1,036` points) in `16 ms`. The page then does two things that do not scale with path length:

1. `renderNode` renders the visible tree as **nested `<ul>` lists, one nesting level per comb level**, in one `innerHTML` string. A go-to along a path of `1,365` levels produces a DOM nested `1,365` deep. Browsers either cap element nesting (Blink flattens past `512`) or exhaust the renderer's stack during layout and style recalculation on nesting that deep — a tab crash, which is what the author saw. Deep nesting is also what makes the page `27,000` px wide (one indentation step per level).
2. `gotoState` calls `ensureKids` and sets `expanded = true` on **every** ancestor, so all their children are rendered — `4,425` cards for this input — when only the path child of each ancestor is needed to place the node.

## The fix — required changes

1. **Flat rendering.** Render the visible nodes as a flat sequence of rows (one `<div>` or `<li>` per visible node in a single flat container; no `<ul>` inside `<li>`). Depth-first order as now, so the reading order is unchanged. Indentation is a style computed from the level, **capped**: `margin-left = min(level, 24) × step`, so the page never grows wider than the viewport by more than one card. The level is already printed on every card, so nothing is lost when the indentation saturates. The maximum DOM nesting under the tree container must be bounded by a small constant independent of the path length — make that a checked property (item 5).
2. **Path-only expansion on go-to.** Along the go-to path, each ancestor is expanded to show **only its path child**, plus one greyed stub row `+ k more children (expand)` for the remaining children (and the dead-door / excluded-self-loop rows folded into that stub). Clicking the stub expands the rest for that ancestor only. Ordinary click-expansion of a node shows all its children as before. The go-to message states the count: "placed at level λ; 1,364 ancestors on the path shown, each with the rest of its children behind a stub".
3. **An explicit reading of comma input.** `137,517` is read as the state `(137, 517)`, which is what the original brief specified, but a comma is also how people write `137517`. Keep the state reading and make it visible and reversible: the message after a go-to with a comma input must begin "read as the state (137, 517) — for the odd integer 137517, type it without the comma", with the integer alternative as a clickable link that performs that go-to. If the comma reading is not a valid state but the digits joined are a valid odd integer, say so and offer the integer reading the same way.
4. **A guard on what is rendered.** If a go-to path exceeds `5,000` nodes (the cap on `pathToRoot` stays at `10,000`), place the node but render only the last `200` ancestors below the root region and a single row "… N ancestors not shown (levels a..b)" between; say so in the message. This should never trigger for typed input, but the page must degrade, not crash.
5. **Check script extension.** `experiments/comb_explorer_check.py` gains a rendering test under the stubbed-`document` harness the findings describe: go-to `(137, 517)`, go-to `213`, go-to the state of a random `300`-digit odd integer, then measure on the produced tree HTML (a) the maximum element nesting depth under the tree container, which must be at most a small constant that the script states (expected `3` or less), (b) the number of rendered rows, which must equal the number of visible nodes (path length plus stubs) and not the number of all children, and (c) no exception. Print the three numbers per case. The existing arithmetic comparisons stay as they are (`15,291` checks) and the new checks add to the TOTAL. **One command reproduces the committed output** (`python experiments/comb_explorer_check.py`); run it in the foreground and wait; commit the new output.
6. **Self-test** stays on load; add the (137, 517) path length and `η`, `λ` as canaries (`1364`, `1056`).

Nothing else on the page changes: the node card, the detail panel (path to root, raw descent, sibling chain), the level census, the vocabulary, the isolated core with its markers. The core itself needs no change; if you find you must change it, say why in the findings.

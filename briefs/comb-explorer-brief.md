## The deliverable: `viz/comb_explorer.html`

One self-contained HTML file in the house style. No external scripts, styles, fonts or images; nothing fetched; works from `file://`. All integer arithmetic in `BigInt`; no floating point anywhere a displayed integer or a decision depends on it. Must remain usable when integers reach hundreds of digits (level 27's largest peak is `2^55`, but a branch followed upward through cascade edges quadruples the peak each level, and door children grow too): render integers longer than about 24 digits abbreviated as `first 8 digits … last 4 digits (N digits)` with a click-to-reveal of the full value, and never let a long integer break the layout.

**The arithmetic core, isolated.** Put every function that computes anything in one `<script>` block delimited by the exact comment lines `// === COMB CORE BEGIN ===` and `// === COMB CORE END ===`, with no DOM access inside, so the block can be extracted and run under node. Functions, all on `BigInt` (states as `[ω, d]` arrays of `BigInt`):

- `v2(n)`, `v3(n)`;
- `exitData(ω, d)` → `{A, s, y}` with `A = 3^d ω − 1`, `s = v2(A)`, `y = A / 2^s` (the peak, the branch, the door);
- `stateOfOdd(y)` → the state whose door `y` is (door recovery: `y + 1 = 2^m 3^a Ω`, state `(Ω, m + a)`);
- `F(ω, d)` = `stateOfOdd(y)`;
- `doors(Ω, D)` → the list `[{a, y, alive}]` for `a = 0 … D−1`, `y = 2^{D−a} 3^a Ω − 1`, `alive = (y mod 3 ≠ 0)` (only `a = 0` can be dead, Theorem 14.5.1);
- `parent(ω, d)` → `{state, type}`: for `s ≥ 3` the cascade parent, the state at branch `s − 2` on door `y`; for `s ≤ 2` the door parent `F(ω, d)`; the root `(1,1)` has no parent (return `null`);
- `children(Ω, D)` → the list of `{state, type, s, door: {a, y}}`: the cascade child (branch `s + 2` on the node's own door, `type = "cascade"`) and one door child per live door at its lowest admissible branch (`s = 1` if `y ≡ 1 (mod 3)`, `s = 2` if `y ≡ 2`, `type = "door"`), with the root's self-child `(1,1)` excluded; dead doors are returned separately as `{a, y, dead: true}` so the page can show them greyed;
- `rawDescent(ω, d, a)` → the block's raw trajectory from the representative `x_a = 2^{d−a} 3^a ω − 1` down to the door `y`: the list of integers `x_a, 2x_{a+1}, x_{a+1}, …, 2A, A, A/2, …, 2y, y`, each tagged as odd point / rising-run even / peak-of-this-node / peak-of-lower-sibling (with that sibling's state) / non-peak cascade even, per Proposition 18.4.1 — the peaks of lower siblings on the same door are exactly the even cascade points `2^j y` with `j < s` and `2^j y ≡ 2 (mod 3)`;
- `pathToRoot(ω, d, cap)` → the parent chain `[node, parent, …, (1,1)]` with a step cap (return what was reached and a flag if the cap hit), and from it `η = 1 + (door edges)` and `λ = (edges)` — the corrected law, Proposition 18.3.2(b); at the root `η = λ = 0`.

**The page.**

1. **The tree.** Starts with the root `(1,1)` at level `0`, its one child `(1,2)` shown as a collapsed stub (with the root's own door `1` shown once, marked "its lowest-branch child is the root itself, the excluded self-loop"). Clicking a node's disclosure control expands it one level: its cascade child first, then its door children in door order `a = 0, 1, …`, then the dead top door greyed if the top door is dead. Expanding is the only way nodes appear; nothing is precomputed beyond what is shown. Collapsing hides the subtree without forgetting it. An indented nested list, not a canvas: horizontal position is the level, edge type is visible on each node (a label or a distinct marker for *cascade* versus *door*, colour-blind safe — use a glyph or word, not colour alone).
2. **The node card.** Each node shows: the state `(ω, d)`; its peak `A`; `A = 2^s · y` read as "branch `s` on door `y`"; `λ` (its level, exact by construction) and `η` (from the path to the root, exact); its parent edge type; and, for a door child, which door of the parent it came through (`top` or `side a = …`). Selecting a node (click on the card, distinct from the disclosure control) opens the detail panel.
3. **The detail panel (selected node).** (a) The path to the root as a breadcrumb: every node from here to `(1,1)`, each with its edge type, and the tally `λ = … edges = … door + … cascade`, `η = 1 + door = …`. (b) The raw descent: the block's raw trajectory from the node's top door (or from any of its representatives, selectable) down to its exit `y`, with the peaks of lower siblings on that door marked and named — this is the author's "orbits falling along `s`" made visible, and it must cite Proposition 18.4.1 in one line. (c) The siblings on this door: the chain of branches `s₀, s₀+2, …` up to this node and two beyond, with their peaks `A, 4A, 16A, …`.
4. **Go to a node.** An input accepting either a state `ω,d` or a positive odd integer `x`. For `x`, compute its state `stateOfOdd(x)` (every odd integer is the door of exactly one state, 14.6.5.1) and say so. Then compute the path to the root (cap `10,000` steps; say if the cap hits — it will not for any input a person types, but the page must not hang), expand the tree along that path so the node appears at its true level with its ancestors, select it, and scroll to it. This is the downward direction of exploration: the tree grows only upward from the root by expansion, and the go-to lets the author drop in anywhere and see the comb path down.
5. **Level context.** Wherever a level number is shown, show the census count for that level from comb.md 18.5's table (embed the 28 counts for levels `0..27` as constants; beyond `27` say "beyond the census"). One line under the tree: "levels double from about level 17; the largest peak at level `λ` is `2^{2λ+1}`, on door `1`" (Lemma 18.5.1).
6. **Reading aids, in the register of the record.** A short paragraph at the top saying what the comb is and what a click does, with pointers to comb.md §18 by section number; the vocabulary used exactly as the registry has it (peak, comb, cascade edge, door edge, top door, side door, live/dead door, `η`, `λ`); no family-frame vocabulary (no columns, no tears, no grouping by core). Flat prose; no exclamation marks; nothing claimed beyond what the page computes.
7. **Self-test on load.** The page runs the core against embedded canaries and prints one footer line `self-test: N checks, 0 failures` (or the failures). Canaries, all from comb.md §18 and the findings: the root's only child is `(1,2)`; door `1`'s chain `(1,1), (1,2), (11,1), (43,1), (19,3)` at branches `1, 3, 5, 7, 9`; door `5`'s states `(7,1), (1,4), (107,1)` at `s = 2, 4, 6` with peaks `20, 80, 320`; `(7,3)`'s children `(251,1)` (cascade, peak `752`), `(37,1)` through the top door `55` at `s = 1`, `(37,2)` through side door `83` at `s = 2`, `(167,1)` through side door `125` at `s = 2`; `(1,2)`'s top door `3` dead; distances `(1,2): η = 1, λ = 1`; `(11,1): η = 1, λ = 2`; `(7,1): η = 2, λ = 2`; `(107,1): η = 2, λ = 4`; the raw descent of `(107,1)` from its entry `213` is `213, 640, 320, 160, 80, 40, 20, 10, 5` with `80` and `20` marked as the peaks of `(1,4)` and `(7,1)`; and `parent(child) = node` for every child of `300` deterministic pseudo-random states (a fixed linear-congruential sequence, so the test is reproducible, no `Math.random`).

## Verification: `experiments/comb_explorer_check.py`

Fresh Python, imports nothing from any existing script. It (1) reads `viz/comb_explorer.html`, extracts the text between the two core markers, and runs it under `node` (available on this machine, v20) with a small harness appended that evaluates the core on a list of inputs read from stdin as JSON and prints JSON; (2) implements the same rules independently in Python with exact integers — `exitData`, `stateOfOdd`, `F`, `doors`, `parent`, `children`, `rawDescent`, `pathToRoot` with `η` and `λ` — from comb.md §18's definitions, not from the JavaScript; (3) compares the two on the canaries above and on `2,000` random states (`ω < 10^6`, `3 ∤ ω`, `d ≤ 40`; seed printed) for every function, plus `300` random odd `x < 10^12` for the go-to path (`η`, `λ`, and the full path), plus `200` random representatives for the raw descent; (4) prints per-function counts and `TOTAL: checks = N, failures = 0`. **One documented command reproduces the committed output in full** (`python experiments/comb_explorer_check.py`). Run it in the foreground and wait for it; commit the output as `experiments/comb_explorer_check_output.txt`. If `node` is missing on a future machine the script must say so and exit non-zero, not pass vacuously.
